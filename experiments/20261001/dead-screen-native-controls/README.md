# Private native Dead Screen controls — preparation only

This plan uses the exact held V5 candidate (`KERNEL64S.BIN`, 664026 bytes, SHA256 `d050560d5c535482c08d442b05fdc7db2650b86f6b3a7290ac5d5f3131ab9114`) and unchanged original UEFI loader, WIN64 archive, OVMF code and variable template. The normal/default kernel and `run_k64_gop.py` remain unchanged. All boot images here are new and have never been booted. They contain no Windows 98 image or original modern target application.

The three cases select exactly one private normal-startup token: `shz.dead-screen-panic-control`, `shz.dead-screen-ud-control`, or `shz.dead-screen-text-control`. Existing normal GUI/input initialization precedes the deliberate own-kernel failure. The fault handler cannot resume the kernel. This tests standalone Shizuku Kernel64 controls; it does **not** test Win98/VMM interception, recoverable Win98 dialogs, arbitrary fault-stack unwinding or modern app readiness.

Run `python3 prepare.py` only once in this new version. It prepares and reads back fresh FAT16 members, compiles a held-header ABI observer and held-C transport reference, runs host refusal/protocol controls and freezes `plan.json`/`result.json`. It never launches QEMU. Existing scripts are semantic/source lineage only and are not imported or changed. `fatimg.py`'s actual 16-head/63-sector partition geometry, reproducible timestamps and mtools operations are used in private copies, with bounded subprocess calls and whole member readback.

The runner takes only a NEW task-private standalone Kernel64 lane (`build/dead-screen-native-control-plan-20261001-v5/dead-screen-lane.lock`). Preparation creates this unique owned file; the frozen plan pins its canonical path, device, inode and exact bounded contents. Launch refuses a symlink, hardlink, replaced inode/content, missing file or already occupied private lane. All six private sources are new copied V4 files; existing Win98 locks are never opened or changed. Independent external Win98/Android VMs are preserved. This standalone 256 MiB trial uses only its own disk/VARS/socket; the lane serializes these three controls, not unrelated guests. Source, compiler, runtime, firmware and prepared-image handles remain pinned/shared-locked through the owned child lifetime; only newly cloned disk/VARS files are writable. The existing descriptor limit must cover the exact handle closure plus 64 descriptors; it is never overridden. Other host QEMU processes are recorded with PID, executable, start time, cumulative CPU ticks and RSS. Real capacity conflicts still refuse launch. Checks retain 17 GiB + 512 MiB filesystem reserve plus 1 GiB run headroom and 7 GiB RAM total (6 GiB reserve plus 1 GiB guest/observer). External programs can race resource checks; the private lock is advisory and is not a host-global capacity reservation. Guard-only neither locks nor launches.

Device lineage is the actual unchanged GOP harness: `q35`, `tcg`, `qemu64,vendor=GenuineIntel`, 256 MiB, S3 disabled, no display window, standard VGA/Bochs (`-vga std`), no network, no reboot, pflash code readonly unit 0, private pflash VARS unit 1, private disk `hd0`, `ide-hd` on `ide.0` bootindex 1, `isa-debug-exit` at `0xf4`, COM1 file, and private Unix QMP socket. The candidate's single-CPU assumption changes the inherited harness's `-smp 2` to explicit **`-smp 1`**. An explicit private `-L` ROM directory contains exact copies of the installed standard VGA ROM, SeaBIOS ROM and QEMU helper ROMs. No KVM, guest network, host audio, VM service, global setting or default-image mutation is used.

Each of three sequential children has a monotonic 180-second observation cap (maximum 540 seconds plus cleanup); there is no parallel child. QMP replies have matching IDs, 64-event/64-KiB line/3-second operation limits and real peer PID/UID checks. The runner records the child's PID, `/proc` start token, executable and entire argv, and uses a stable Linux pidfd for cleanup when available. Cleanup is registered **before** spawn and remains valid if token acquisition fails: the Popen-created, unreaped child is its authority. Forced terminate/kill and every timeout are failures. Normal cleanup allows at most five seconds after terminate and five after kill. If the host cannot stop that child, an immediate FAIL receipt is written and the coordinator retains its real source/lock handles until child exit; this exceptional ownership wait has no promised total duration and starts no further observation/child. Returning would silently close handles while the child remained live. Cleanup stops only that exact child before releasing held handles. Normal owner QMP quit is explicitly **not** OS exit success; the intentional fatal loop cannot exit successfully. Any actual `SHZ-EXIT:` serial marker fails the no-resumption check.

Native evidence would consist of paused, bounded known-BSS physical reads and real QMP screenshots, never raw disk reads or arbitrary memory scans. ELF STT_FILE ownership identifies `native.c` state at physical `0x265180` (1352 bytes), framebuffer at `0x265140` (40), and first immutable fault `state[0:424]`. The held ELF/loader/final page tables map the kernel alias `0xffffffff80000000` to physical zero, with BSS ending at `0x2656c8`, below the unchanged 3 MiB heap boundary. The actual control `UD2` bytes are `0f 0b`, linked IP `0xffffffff8018e31f`; its saved record must show vector 6, error 0, ring0 CS and actual-frame marker. Live QMP CPU registers are captured separately and **differ** from saved fault registers after handler entry. No fabricated host register values are substituted. Supervisor-domain EPT is unsupported by this direct-boot runner.

Panic and #UD controls exercise real PS/2 keys: KO/EN menu, Tetris move/rotate/gravity/drop/restart, Suika aim/drop/gravity/deterministic real-key merges/restart, trace/items and menu return. First-record bytes must remain unchanged throughout. Text control checks the exact complete English serial record and ASCII framebuffer, then verifies key input does not resume games. The same-source host rendering reference detects completed framebuffer publication/transport, and is labelled as such; it is not an independent specification of game artwork. Every claimed native observation needs the real record, actual keys and real captured pixels. Screenshot retries are bounded and a partially painted frame cannot count as a completed capture. A slow or unavailable PIT/PS2/GOP path fails truthfully. The record explicitly keeps `app_success`, `win98_vmm_acceptance` and `os_exit_success` false.
