# Interface facts and provenance

No external driver or loader implementation was copied. The COM and its tests are
original. Interface names, constants, register contracts and file-format facts
were read from these sources.

* [Microsoft Windows 3.0 DDK, Virtual Device Adaptation Guide, Appendix D.1.6](https://www.pcjs.org/documents/books/mspl13/win/w3ddkvxd/): INT 2Fh AX=1684h/BX=device ID returns the V86 far-call entry in ES:DI. Initialize ES:DI to zero before discovery. This documents the discovery mechanism, not Win98-specific loader behavior.
* [Microsoft Systems Journal, May 1995, Walter Oney's Windows 95 VxD article, PDF pages 51–52](https://jacobfilipp.com/MSJ/1995/1995-05.pdf): the DOS-side load function is AX=1 with DS:DX filename; the by-name unload example uses AX=2, BX=FFFFh, DS:DX DDB short name. Only interface facts were used, not the published DEBUG implementation. This is an original Windows 95 account, not a Win98 execution receipt.
* [Archived original Win98 DDK VMM.INC](https://github.com/fapablazacl/win98-ddk-toolchain/blob/0c662d32378b9940ed90aee682f4eb5daf816e6a/98DDK/inc/win98/VMM.INC), pinned archive commit `0c662d32378b9940ed90aee682f4eb5daf816e6a`, 88,624 bytes, SHA-256 `d640c2994970fabe36c6d4f47ac94b719554d19dc036807c56fe9252ded6d1b2`: VXDLDR device ID 0027h. An identifiable archived Microsoft header, not a current Microsoft download.
* [Archived original Win98 DDK VXDLDR.INC](https://github.com/fapablazacl/win98-ddk-toolchain/blob/0c662d32378b9940ed90aee682f4eb5daf816e6a/98DDK/inc/win98/VXDLDR.INC), same commit, 2,738 bytes, SHA-256 `c3ae781a955721d5f083bef052850404e1a7b16be200a955ea6353c6557f1f08`: API numbers 0/1/2, named loader errors 1–11. The ring-0 service table is distinct from this V86 entry and is not invoked by the COM.
* [Geoff Chappell, Dynamic VxD Loading in Windows for Workgroups 3.11](https://www.geoffchappell.com/notes/windows/archive/vxdldr.htm): first-person historical description of raw CF/AX completion, function-0 DX version, combined load/init, and the older BX=0 by-name convention. That older unload convention is **not** used here. Version values are logged without asserting they are Win98 values.
* [Microsoft MS-DOS 3.3 Programmer's Reference](https://www.pcjs.org/documents/books/mspl13/msdos/dosref33/): COM initial segment/stack setup; INT 21h functions 3Dh, 3Eh, 3Fh, 40h, 4Ch and 5Bh. Function 5Bh creates a new file without truncating an existing one; counted I/O requires testing the returned byte count. The diagnostic uses no DOS resident installation or interrupt-hook changes.

Host tooling is NASM/ndisasm plus [Unicorn 2.1.4 official PyPI metadata](https://pypi.org/pypi/unicorn/2.1.4/json). The CPython abi3 Linux x86-64 wheel used for this experiment is 16,436,886 bytes, SHA-256 `9d6e6dea140560de4ebd8446661f7ef84a357d428c14a3ef09dacd306ec8c239`. It was verified against that metadata and extracted into a new private RAM directory; there is no system/global install and no OS/runtime dependency. Test code models the interrupts and far-entry behavior. The CPU execution is independent tooling; the synthetic environment is not Windows.
