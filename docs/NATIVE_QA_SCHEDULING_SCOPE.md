# Native Win98 scheduling scope

The earlier broad queue wording in the CSS stage handoff and root coordination
notes was a conservative project interpretation. This operational addendum
supersedes that wording without changing any frozen source, receipt or stage.

The exact `zuku-legacy-browser-lab/SKILL.md` says:

> Both paths permit only one QA VM at once; preserve 6 GiB host memory and 20 GiB disk headroom.

Its preceding sentence identifies the ZUKU libvirt profiles and the separate
upstream-QEMU Windows ME path under `/home/almalinux/workspace/zuku-platform`.
It does not define a host-wide prohibition covering this independent Win98
project and separate Kernel64 application runners. No Win98 worktree AGENTS.md
adds that prohibition. Existing frozen guest receipts remain evidence of their
actual former queue decisions.

Our Win98 native trials still require one owned guest, the cooperative native
flock, vacancy of other actual Win98 native run disks (including peers outside
that flock), at least 6 GiB available host memory and the unchanged 20 GiB disk
reserve plus measured cold-copy, dirty-write and staging allowance. Check actual
open image descriptors and positively identified project/scenario evidence;
do not infer a guest's OS solely from an application-media filename. Unknown
Win98 native candidates remain blockers until their identity is resolved.

Separate positively identified XP or standalone Kernel64 runners do not consume
this Win98 slot. Their memory/disk use still counts in fresh headroom checks.
Never stop a peer, alter its disk or control its GUI to obtain a slot. Use a new
private cold copy, private firmware variables and no network, retain originals
and hashes, and stop only the guest owned by this trial. Each new trial must
recheck the queue and resource floor, and each component still needs its actual
native logs, independent child exit and separately reviewed paint evidence.
