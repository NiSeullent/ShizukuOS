## Step 2 — the second export batch (done, verified)

The batch was first written while the shell was unavailable and committed unbuilt (commit "second export batch … unverified as
committed"). It was then built and debugged under QEMU; every fix below was found by running it.

Verification: `python3 shizukudos/tests/run_k64_ntdrv.py --accel tcg --timeout 600` → **PASS 13/13**, providers = **572**
(553 ntoskrnl + 19 hal), `APITEST.SYS` **99 PASS / 0 FAIL** (`GUEST_RUN`, TCG). `run_k64_standalone.py --accel tcg` → **PASS**.
What is in it and where is described in `NTDRV.md` §2.10–§2.13; the host side of each area is `ntdrv_ex.c`, `ntdrv_crt.c`,
`ntdrv_reg.c`, `ntdrv_dev.c`, `ntdrv_seh.c`, `ntdrv_kuser.c` plus edits to `ntdrv_io.c`/`ntdrv_zw.c`/`ntdrv_mm.c`/`ntdrv_ke.c`/`ntdrv_ldr.c`.

Bugs the guest run found (all fixed): a registry helper declared with the wrong calling convention (`ntdrv_wcslen`, read garbage);
`DEVICE_REGISTRY_PROPERTY` indices shifted by one; work items with an "Ex" routine were called with one argument;
the IRQL is read from `CR8` by WDK inline code (now mirrored); a page fault inside a driver was fatal (now SEH-dispatched).

### Step 2c — SEH
`RtlLookupFunctionEntry`, `RtlVirtualUnwind`, `RtlUnwind(Ex)`, `__C_specific_handler`, `RtlCaptureContext`, `RtlRaiseException` & co., plus a hook so
CPU faults inside a driver reach its handlers; `VfIsVerificationEnabled`/`VfFailDeviceNode` closed the last two ntoskrnl gaps
(`ntoskrnl.exe` **313/313**). Tests: hand-assembled `.seh` functions in `APITEST.SYS` (raise, fault, `__finally`, filter, nesting).

## Step 3 — KMDF (done to the stated milestone)

`python3 shizukudos/win64/ntdrv/kmdf_image.py` builds `WIN64_KMDF.IMG` (test drivers + the corpus's `wdfldr`, `wdf01000`, `cdrom`, `hdaudbus`);
`python3 shizukudos/tests/run_k64_ntdrv.py --kmdf --accel tcg --timeout 600` → **PASS 19/19**:
both KMDF clients' `FxDriverEntry` → `WdfVersionBind` (into the real WdfLdr) → the real `Wdf01000` loaded by `ZwLoadDriver` and registered →
`WdfDriverCreate`; `DriverEntry` returns `STATUS_SUCCESS`, and the framework's `AddDevice`, `DriverUnload` and IRP dispatch (28 major functions)
are on the client's `DRIVER_OBJECT`. This needed export-driver linking (imports resolved against a mapped export table, on-demand load,
forwarders, `DllInitialize` for entry-less images), a per-thread KPCR behind GS (`KeGetCurrentThread` is `gs:[0x188]`), and a
`Services` key for store loads. No provider was written for WDF: the framework's own binaries run.

**Corpus bug found and fixed.** `wdfldr.sys`, `cdrom.sys`, `hdaudbus.sys`, `classpnp.sys` and `disk.sys` carried a `memset` that called itself
(GCC turned the CRT's byte loop back into a `memset` call), so the first `memset` recursed until the stack was gone. The fix is one flag in
`shizukudos/ntdrv/corpus/build.py` (`-fno-tree-loop-distribute-patterns`); those five were rebuilt. **Any other checkout must re-run
`corpus/build.py` for the corpus binaries to match.**

## Merge with N3's work (the lead branch moved twice)

The lead branch gained N3's driver-load work (`wip/n3-driver-load`, PRs #6–#11: `shzpnp load`, PnP root, export-driver loading, per-thread `CR8`,
`ntdrv_pnp.c`, 40 exports) while this branch was being built, and later W1/W3's WebKit work. Both merges were done with merge commits (no rebase).
Where N3 and this branch implemented the same thing, one implementation was kept:

| Area | Kept | How |
|---|---|---|
| IRQL | N3's: `CR8` is the only copy, saved per thread, ISRs at DIRQL | this branch's software `g_irql` mirror was dropped; the KPCR/GS support was kept on top |
| Export-driver loading | N3's (users counting, dependency flag, import-cycle guard, `\SHZ\SYS64\DRIVERS`) | added: forwarders into ntoskrnl/HAL, `DllInitialize` for entry-less images, `\SHZ\DRIVERS` as a second store path |
| `NtLoadDriver`/`NtUnloadDriver` | N3's (serialised by a mutex, `NtUnloadDriver`, `NtShzDriverQuery`) | this branch's kernel-mode `ZwLoadDriver`/`ZwUnloadDriver` call the same core and skip the mutex when the calling thread already holds it (WdfLdr loads its library from inside a client's `DriverEntry`) |
| PnP root, PCI-function PDOs, `BUS_INTERFACE_STANDARD`, start IRPs | N3's `ntdrv_pnp.c`, unchanged apart from removing exports that are now generic | |
| Generic exports both had (driver-object extensions, shutdown notifications, `PoCallDriver`, DMA adapters, `HalTranslateBusAddress`, SList/Ex lists, `Rtl*` strings, `RtlQueryRegistryValues`, `wcs*`, `ZwEnumerateKey`, `ZwQueryInformationFile`, `ExQueueWorkItem`, bug-check callbacks) | this branch's (covered by the 99 `APITEST.SYS` checks) | N3's copies deleted |
| Exports that depend on the kind of PDO (`IoGetDeviceProperty`, `IoOpenDeviceRegistryKey`, `IoRegisterDeviceInterface`, `IoSetDeviceInterfaceState`) | both | exported from `ntdrv_dev.c`, which calls N3's `n3_*` versions for the PDOs of PCI functions and serves legacy root-enumerated devices itself |

The merged tree exposed one real difference: N3's NIC install stores `Linkage\Export` as `REG_MULTI_SZ`, and NDIS reads it with a `DIRECT` query into a
`UNICODE_STRING` with no buffer; this branch's `RtlQueryRegistryValues` rejected that (`STATUS_INVALID_PARAMETER`, so the e1000 `AddDevice` failed). Fixed to
Windows' behaviour and covered by a new `APITEST.SYS` check.

`shizukudos/upstream/manifest.json` on the lead branch was not valid JSON (the WebKit/ICU entries had been inserted inside the `publicsuffix-list`
entry), which stopped `win64/build.py`; one missing `"patches": [], }` was restored.

Verified on the merged tree (all `--accel tcg`, all PASS): `run_k64_ntdrv.py` (default 13/13, `--kmdf` 19/19, `--corpus` 21/21), `run_k64_pnp.py` (N3's
e1000 + ndis.sys start, 24/24), `run_k64_standalone.py` (T_DRV_LOAD, T_SHZPNP, ...), `run_k64_gui.py`, `run_k64_net.py`.

## Not done / BLOCKED / caveats

- **"K for the Intel Win10 list" — BLOCKED (no measurable list exists here).** There is no Intel driver package or import list in the repository or
  in this session, and none was invented. Run `import_coverage.py <package dir> --ntoskrnl build/shizukudos/win64/ntdrv --export-drivers --rank intel.md`
  on the real package to get the number.
- A KMDF client that goes on to create devices, queues and interrupts (`AddDevice` → `WdfDeviceCreate`) has not been driven; only binding and
  `WdfDriverCreate` are verified.
- "Loaded, `DriverEntry` succeeded" for the corpus is not "drives hardware"; only the three test drivers drive a device (QEMU `edu`).
- TCG only, no KVM/VMX. Kernel stacks are 32 KiB; the SEH walk uses a few CONTEXTs per level, so very deep exception nesting is not tested.
- Only driver images carry `.pdata`, so an exception with no handler in the driver frames is a bug check, and drivers built without unwind data
