# Windows 98 registry restoration persistence

This checkpoint compares only file metadata from one immutable original disk and three completed private replacement-DOS runs. The actual ShizukuDOS goal is replacing MS-DOS beneath Windows 98; Kernel32, Kernel64 and Supervisor are Windows 98 components. A Registry Checker screen does not establish a running Windows 98 desktop or completed replacement.

Restoration writes really persisted. The completed v6/v7/v9 runs contain identical restored `SYSTEM.DAT`, `USER.DAT`, `SYSTEM.INI` and `WIN.INI` bytes, while their first clusters change. `SYSTEM.DAT` is 2,273,312 bytes and `USER.DAT` is 102,432 bytes; each is 4,096 bytes smaller than the original. Both keep FAT attributes `03` (read-only and hidden). Their exact-size cluster chains are within range, without cycles, and agree between both FAT copies. The numbered backup cabinets retain their original hashes; a separate `RBBAD.CAB` exists after restoration. These observations weaken lost-close/flush/rename as the primary explanation of the repeated restore prompt.

Four complete 2 GiB images were opened read-only with no-follow descriptors and shared advisory locks. Physical whole-image hashes and descriptor identities matched before and after the read. A fresh independent standard SHA256 tool crosscheck subsequently matched all four complete-image digests and unchanged descriptor/path identities. An earlier retry correctly refused a legitimate exclusive source lease before reading that image; it was repeated only after the owner released the closed-source lease. The blocked checkpoint is preserved separately. No image was modified. The current live/later experiment was not opened. The inspector did not extract or print registry contents, usernames, keys or private screenshots. This report publishes only fixed system-file names, sizes, SHA256 digests, FAT attributes and chain metadata.

Five bounded synthetic reader tests passed for file hash/attribute preservation, cyclic and short chains, FAT-copy differences, and out-of-image geometry. Those tests are parser checks. The physical metadata came from the private images and remains separately pinned in `summary.json`; it is not inferred from synthetic tests. Chain checks are per selected file, not a complete filesystem or registry-format verifier. Internal hive validity, trigger flags, memory adequacy and Windows protected-mode initialization remain unknown.

A later source-only reader followup adds exact-length whole-image reads and full-write handling. Its three negative/partial-I/O fixtures first failed and then passed. That followup did not inspect private images and does not replace the original metadata producer provenance.

Memory is a separate requirement. Microsoft's original KB183887 says repair may need “580 KB or more of free conventional memory,” and extended memory is also required except for `/restore`. An XMS allocation/move test therefore does not establish adequate conventional memory. The legacy official support URLs can redirect or become unavailable; the [Microsoft-authored archived KB183887 text](https://mskb.pkisolutions.com/kb/183887) preserves these requirements. The [Microsoft Registry Checker command-line documentation](https://support.microsoft.com/en-au/topic/command-line-switches-for-the-registry-checker-tool-9b2efea9-9edd-fd11-261e-83075f141f68) originally distinguishes the MS-DOS and Windows checker syntax; their switches should be traced rather than guessed. On this check, the live command-line URL redirected to generic Windows help and the archive was unavailable. These facts were rechecked against the original Microsoft-authored article bodies returned by the search index; the generic landing page is not supporting evidence. The limited authority receipt is pinned in `summary.json`.

The next owner-controlled diagnosis should measure the actual largest conventional block and real HMA flag before `WIN.COM`, then observe which child checker and command tail are launched. If memory is adequate, trace actual file-open, read/write byte counts, seeks, attributes, rename, close/commit and extended errors without logging hive data. A private original-MS-DOS control using the same restored files can distinguish DOS API behavior from a genuinely invalid registry. Such a control is a diagnostic reference; final acceptance still requires native Windows 98 above ShizukuDOS. No success flag, version, codepage or ScanReg outcome is fabricated here.

Source review confirms the existing close/commit path flushes real drive buffers. Active codepage 949 and system codepage 437 come from separate NLS fields; this difference alone does not establish corruption. ASCII registry filenames and file payload reads are not transcoded by the DOS file layer. Non-ASCII pathname/DBCS handling and unsupported extended DOS APIs need actual call traces before proposing a compatibility fix.
