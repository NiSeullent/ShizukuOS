### 1.3 Why not Ubuntu's libstdc++ (reproduced by W3 with W1's first toolchain, `b8f4928`)

Linking the dependency checks statically with W1's first toolchain gave the same three errors W1's `jsc.exe` link gave:
`duplicate symbol: std::type_info::operator==` (ICU vs `libstdc++.a(tinfo.o)`: GCC predefines
`__GXX_TYPEINFO_EQUALITY_INLINE=0` for mingw, clang does not); `undefined symbol: std::__once_callable` (libstdc++ keeps
its `thread_local`s in emulated TLS, `__emutls_v._ZSt15__once_callable`); `undefined symbol:
std::codecvt<wchar_t, char, _Mbstatet>` (libstdc++ built for msvcrt's `int mbstate_t`). The first two can be flagged
around (`-D__GXX_TYPEINFO_EQUALITY_INLINE=0`, `-femulated-tls`), the third cannot.

## 3. The Shizuku port (design; not yet built)

### 3.1 Choice: a minimal custom single-process port on the Windows port's code

The upstream Windows port is WebKit2 only (UI/Web/Network/GPU processes over IPC, MiniBrowser), depends on ANGLE on
Direct3D 11 for Skia, on Media Foundation, and on MSAA/OLE; WebKitLegacy (single process) was removed for Windows. The
task asks for single-process first. So `PORT=Shizuku`: WebCore + a small embedding layer, reusing the Windows port's
WebCore platform code. Facts that shaped it:

- An unknown port on `OS(WINDOWS)` is `PLATFORM(WIN)` (`wtf/PlatformLegacy.h`), so WebCore's Windows code paths apply
  unchanged; Shizuku differences are `USE(SHIZUKU)`.
- WTF uses the Windows port's Win32 message-pump RunLoop (`RunLoopWin`), which WebCore's Windows code assumes. What it
  needs from user32 was checked in the guest first: `port/tests/t_wk_msgloop.c` (message-only window, `PostMessage`
  from another thread, `SetTimer`/`WM_TIMER`, `PeekMessage` + `MsgWaitForMultipleObjectsEx`) — **PASS** (7 checks,
  117 ms), `GUEST_RUN` with the vga display.
- No GPU: Skia's Ganesh/GL code stays compiled against the Khronos headers in WebKit's `Source/ThirdParty/ANGLE/include`
  (ANGLE itself is not built) and links `port/egl/shzegl.c`, an EGL whose display query fails; the embedding sets
  `ProcessCapabilities::setCanUseAcceleratedBuffers(false)`, so WebCore paints through its unaccelerated Skia backend.
- Fonts: FreeType through Skia's directory font manager on the system font directory (`\SHZ\FONTS`: Noto Sans/Serif/
  Mono, Tahoma) instead of DirectWrite: `port/patches/0001` (Skia CMake `USE_SHIZUKU` branch, `FontCacheSkia.cpp` uses
  `port/webcore/FontManagerShizuku.cpp`).
- WebCore sources: the Windows port's list minus the resource-usage overlay, ANGLE (`PlatformDisplayANGLE`,
  `GraphicsContextGLEGL`), full-screen windows and Media Foundation (`port/overlay/Source/WebCore/PlatformShizuku.cmake`).
- JavaScriptCore/bmalloc as W1's `JSCOnly` Windows build (C loop, static).
- Everything static; the embedding and its programs are added from `SHIZUKU_PORT_DIR` (`port/CMakeLists.txt`).

Files: `port/overlay/` (new files copied into the pinned tree: `Source/cmake/OptionsShizuku.cmake`, `Source/{WTF/wtf,
JavaScriptCore,bmalloc,WebCore,WebCore/PAL/pal}/PlatformShizuku.cmake`, `Source/PlatformShizuku.cmake`), `port/patches/`
(changes to upstream files, applied after W1's patches), `port/build_port.py` (driver), `port/shizuku/` (embedding:
initialization, platform strategies, `OffscreenPage`), `port/programs/TWkRender.cpp` (R1), `port/egl/`, `port/webcore/`.
The pin's sparse paths gained `/Source/WebCore/`, `/Source/ThirdParty/skia/`, `/Source/ThirdParty/ANGLE/include/`.

### 3.2 R1 plan

`T_WK_RENDER.EXE <page.html> <out.bmp> [w h]`: a Page with WebCore's empty clients, the document written straight into
the main frame's `DocumentWriter` (WebCore's own `SVGImage` pattern; no loader), laid out at the viewport size and
painted by `GraphicsContextSkia` into a top-down 32-bit buffer; timings printed for section 4. The reference is the same
page rendered on the host by Chromium (Playwright's, pre-installed) with the same Noto font file, compared with a
tolerance.
