## Minimal Electron app

`shizukudos/tests/e1_minapp/` (`package.json`, `main.js`, `index.html`): main opens a hidden `BrowserWindow` on the local
page; the page script sets `document.title = 'electron-min ' + (6*7)`; main reads the title back with
`executeJavaScript`, prints `SHZ-E1-MARKER electron-min 42` (console.log + stderr) and calls `app.exit(0)` (non-zero on
every failure path, 15-minute watchdog exits 4).

HOST_TESTED on Linux with Electron 44.5.0 linux-x64 under `xvfb-run`:
- `electron --no-sandbox --disable-gpu --enable-logging=stderr --v=0 shizukudos/tests/e1_minapp` → marker, exit 0.
- packaged layout (app copied to `resources/app`, `electron --no-sandbox --disable-gpu --enable-logging=stderr --v=0
  --no-first-run`) → `SHZ-E1 main: app ready`, `SHZ-E1 renderer console: SHZ-E1 page script ran: electron-min 42`,
  `SHZ-E1-MARKER electron-min 42`, exit 0.
- the same with `--single-process` → `SHZ-E1 main: app ready`, then `Trace/breakpoint trap`, exit 133. Electron 44 does
  not survive `--single-process`, so the guest runs use the normal multi-process model (unlike `run_k64_chromium.py`).

## Static analysis (HOST_TESTED)

Tree revision: this branch (`wip/k3-chromium-wip` 5b69798 + E1 files; no kernel/runtime change). Runtime built with
`python3 shizukudos/win64/build.py` (x86_64-w64-mingw32-gcc 13-win32), 38 DLLs in `build/shizukudos/win64`.

Commands:
```
python3 shizukudos/win64/tools/startup_chain.py <electron>/electron.exe
python3 shizukudos/win64/tools/startup_chain.py <vscodium>/VSCodium.exe
python3 shizukudos/win64/tools/startup_chain.py <chrome-win>/chrome.exe
python3 shizukudos/tests/e1_import_gaps.py --electron <electron> --vscode <vscodium> --chromium <chrome-win> \
    --json docs/shizukudos10/coverage/e1_gaps.json --md <scratch>/e1_gaps.md
```
`e1_import_gaps.py` (owned by E1) runs `startup_chain.py --json --delay` (unchanged) from every AMD64 image at the top
of each tree (for Chromium: `chrome.exe` and the DLLs; helper executables such as `setup.exe` and
`interactive_ui_tests.exe` are left out) and from every `*.node` addon, checks addon imports of `node.exe` against the
product executable's own exports (Electron's delay-load hook binds them to the running exe; all resolve), and diffs the
result against Chromium's list. Full data: `docs/shizukudos10/coverage/e1_gaps.json`.

### Startup chains (the first thing the guest loader does)

| executable | eager images | load-time imports | unresolved | predicted first loader failure |
|---|---:|---:|---:|---|

| electron.exe (Electron 44.5.0) | 16 | 1,277 | **19** | `WS2_32.dll!GetNameInfoW: not exported by ws2_32.dll` |
| VSCodium.exe (Electron 42.8.1) | 16 | 1,277 | **19** | `WS2_32.dll!GetNameInfoW: not exported by ws2_32.dll` |

The 19 (same set for both Electron executables, all in the executable itself):
`ws2_32!GetNameInfoW` and 18 kernel32 names: `CancelSynchronousIo, CreateSymbolicLinkW, FillConsoleOutputAttribute,
FillConsoleOutputCharacterW, GetConsoleCursorInfo, GetCurrentPackageFullName, GetErrorMode,
GetNumberOfConsoleInputEvents, GetPackageFamilyName, GetProcessIoCounters, NeedCurrentDirectoryForExePathW, ReOpenFile,
ReadConsoleInputW, RegisterApplicationRestart, SetConsoleCursorInfo, SetConsoleCursorPosition, SetConsoleTitleW,
WriteConsoleInputW`. None of them is imported by chrome.exe/chrome.dll: they come from Node (libuv's console/TTY code,
`uv_fs_*` symlink/reopen, `uv_getnameinfo`, `uv_getrusage`/`GetProcessIoCounters`, `uv_cancel` → `CancelSynchronousIo`)
and Electron's app model (package identity, restart registration). **Until these 19 exist, electron.exe and
VSCodium.exe cannot be mapped at all**; everything below them is irrelevant for the first guest run.

The libuv core that the task names is already exported by the Shizuku kernel32 and resolves statically:
`CreateIoCompletionPort`, `GetQueuedCompletionStatusEx`, `PostQueuedCompletionStatus`, `SetFileCompletionNotificationModes`,
`CancelIoEx`, `ConnectNamedPipe`/`CreateNamedPipeW`, `ReadDirectoryChangesW` (implementations in
`shizukudos/win64/kernel32/k32_ipc_io.c`; whether they behave as libuv expects is only testable by a guest run).
`CreatePseudoConsole`/`ClosePseudoConsole`/`ResizePseudoConsole` are not in any import table (node-pty's `conpty.node`
looks them up with `GetProcAddress`) and are **not implemented** in `shizukudos/win64/kernel32` (grep finds nothing):
the VS Code integrated terminal needs them (K4).

Counts: Electron + VSCodium together have 336 distinct unresolved imports (all images, load-time and delay-load);
Chromium (chrome.exe + DLLs) has 290; 97 of the 336 are not in Chromium's list (Electron/Node-specific).

## Not done / limits
- Official VS Code, Discord: BLOCKED by the egress policy (see Inputs).
- The runner's PASS gate is only defined for the minimal app, which has a marker. The default app and VS Code never quit
  on their own, so they can only report the furthest point they reach.
- `run_k64_chromium.py` was not rerun in this session, so there is no Chromium guest baseline here. The claim that
  chrome.exe's closure resolves comes from static analysis only.
- No workaround inside E1's files can get past the loader failure. ws2_32 and kernel32 are KnownDLLs, which the loader
  takes from the system directory only, so a shim DLL next to the executable is ignored. The fix belongs to K4 (kernel32)
  and K5 (ws2_32).
