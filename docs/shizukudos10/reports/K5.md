## 2. Step 1 — VS_VERSIONINFO in every built image; version.dll search order (commit "version resources")

* `shizukudos/win64/tools/verres.py` (new): generates a VERSIONINFO `.rc` per image and compiles it with mingw windres
  (`-O coff` for GNU ld, `-O res` for lld-link). File/product version 10.0.22631.1 = the OS version Kernel64 puts in every
  PEB (`kernel64/ldr.c`), so a program that derives the Windows version from `kernel32.dll`'s file version (Chromium's
  `base::win::OSInfo::Kernel32BaseVersion`) sees what `GetVersionEx` says. FILETYPE VFT_DLL / VFT_APP, one language block
  040904b0 (CompanyName, FileDescription, FileVersion, InternalName, LegalCopyright, OriginalFilename, ProductName,
  ProductVersion), Translation 0x0409/0x04b0.
* `win64/build.py`: `version_obj()` links one into ntdll.dll, kernel32.dll (build.py's link lines; no source under
  `kernel32/` or `ntdll/` was touched), every `dlls/<name>/` module (`module.json` "description" = FileDescription),
  every `tests/t_*.c` app (an app with its own `.rc` gets it compiled together with the version block into the one
  `.rsrc` object; `t_u_version.rc` already defines a VERSIONINFO and keeps it), SHZSETUP.EXE, the `apps/` programs,
  the MSVC-ABI C++ tests (lld-link takes the `.res`) and t_ntdrv.exe.
* `win64/wineport/build.py`: a Wine module whose `.rc` does not include `wine/version.rc` (dwrite, propsys, imagehlp,
  cryptbase, cryptsp, cryptnet) and every T_WINE_*/T_WP_* test executable get the generated resource; crypt32, dwmapi,
  rsaenh and wintrust keep Wine's own version.
* Verified with pefile on the host: **122 of 122** DLLs and EXEs in `build/shizukudos/win64` (wineport tests included)
  carry an RT_VERSION resource; the only images without one are the three unmodified test drivers
  `ntdrv/*.sys` (not DLLs/EXEs, not touched).
* `dlls/version/version.c`: a bare name (`kernel32.dll`, or `advapi32` without an extension) is located the way
  `GetFileVersionInfo` does on Windows (LoadLibraryEx as a data file): application directory, system directory
  (`C:\SHZ\SYS64`), current directory, `.dll` appended when there is no extension. New: `GetFileVersionInfoSizeExW`,
  `GetFileVersionInfoExW` (FILE_VER_GET_* validated; without MUI satellites they select nothing).
* Tests: `t_u_version.c` now reads kernel32.dll (bare name and full path), ntdll.dll, version.dll, `advapi32`, user32.dll,
  crypt32.dll (Wine's version), dwrite.dll (generated) and T_HELLO.EXE and checks FILETYPE, 10.0.22631.1 and the

  (`EnumResourceTypesW` now sees RT_VERSION next to RT_RCDATA and SHZTYPE) were updated for images that carry a version

## 3. Step 2 — iphlpapi.dll (new, `dlls/iphlpapi/iphlpapi.c`, test `t_u_iphlpapi.c`)

The first runtime blocker (section 1b). Own GPL-2.0-only code over the Kernel64 stack (`NtShzNetQuery` classes 0-4:
NIC/DHCP state, stack counters, the TCP table, control), exactly two interfaces described with Windows' vocabulary:
index 1 "Loopback Pseudo-Interface 1" (IF_TYPE_SOFTWARE_LOOPBACK, 127.0.0.1/8, MTU 0xffffffff) and, when the machine has
the RTL8139, index 2 "Ethernet" (IF_TYPE_ETHERNET_CSMACD, the MAC, the DHCP address/mask/gateway/DNS, OperStatus from
the link). LUIDs {type, NetLuidIndex 0/1} so names are `loopback_0` / `ethernet_1`, the form Windows produces.

Exported (55): GetAdaptersAddresses (buffer protocol ERROR_BUFFER_OVERFLOW, unicast/DNS/gateway/prefix lists, the three
Windows prefixes per IPv4 address, Dhcpv4Server, LUID, GUID text as AdapterName), GetAdaptersInfo, GetInterfaceInfo,
GetNetworkParams, GetPerAdapterInfo, GetIfEntry/GetIfTable (MIB_IFROW with `\DEVICE\TCPIP_{guid}`), GetIfEntry2/
GetIfEntry2Ex/GetIfTable2/GetIfTable2Ex/FreeMibTable (MIB_IF_ROW2 with the kernel's packet counters), GetIpAddrTable,
GetUnicastIpAddressTable/Entry, GetIpInterfaceEntry/Table, GetIpForwardTable, GetBestInterface/Ex, GetBestRoute2
(on-link vs. gateway, loopback for 127/8 and the own address), GetIpStatistics/Ex, GetTcpStatistics/Ex,
GetUdpStatistics/Ex (kernel counters; octets the kernel does not count are 0), GetTcpTable (kernel class 2),
GetNumberOfInterfaces, ConvertInterface{IndexToLuid,LuidToIndex,LuidToGuid,GuidToLuid,LuidToNameA/W,NameToLuidA/W,
LuidToAlias,AliasToLuid}, if_indextoname, if_nametoindex, IpRenewAddress (real: kernel DHCP renew, control 1),
IpReleaseAddress (ERROR_NOT_SUPPORTED: the kernel has no release), NotifyAddrChange/NotifyRouteChange
(ERROR_IO_PENDING + OVERLAPPED completion, or blocking), CancelIPChangeNotify (STATUS_CANCELLED), NotifyIpInterfaceChange,
NotifyUnicastIpAddressChange, NotifyRouteChange2, CancelMibChangeNotify2. Change detection: the kernel has no
address-change event, so one watcher thread polls `NtShzNetQuery(0)` every 500 ms while a registration exists (documented
in the file header). IPv6: no rows (the stack is IPv4 only); MIB owner-PID classes: not provided (the kernel does not
record the owner of a connection).

`t_u_iphlpapi.c` (≈70 checks) cross-checks every table against `NtShzNetQuery(0)` (the same ground truth
`t_net_nic.c` uses) and adapts to a machine with or without a NIC; the standalone profile has none, so the Ethernet
branches are exercised only under `run_k64_net.py` (not run in this session: BLOCKED by time, not by a failure).

## 4. Step 3 — dbghelp.dll (new, `dlls/dbghelp/dbghelp.c`, test `t_u_dbghelp.c`)

The second runtime blocker. Own code over kernel32's module list (K32EnumProcessModules/K32GetModuleInformation/
K32GetModuleFileNameExW), PE export tables and CodeView records read from the process (ReadProcessMemory for another
process), the x64 unwind tables (RtlLookupFunctionEntry/RtlVirtualUnwind) and the kernel32 process/thread information.
No PDB exists here, and nothing pretends one does:

* SymInitialize/W, SymCleanup (one table per process handle; a second SymInitialize = ERROR_INVALID_PARAMETER),
  SymSetOptions/SymGetOptions, Sym{Get,Set}SearchPath{,W}, SymRefreshModuleList, SymGetModuleBase64,
  SymGetModuleInfo64/W64 (TimeDateStamp, CheckSum, SizeOfImage, SymExport/SymNone, PdbSig70/PdbAge/LoadedPdbName from the
  RSDS record, PdbUnmatched), EnumerateLoadedModules64/W64.
* SymFromAddr/W, SymGetSymFromAddr64: the nearest preceding export (SYMFLAG_EXPORT, SymTagPublicSymbol) - what dbghelp
  reports for a module without symbols. SymGetLineFromAddr64/W64: FALSE, ERROR_INVALID_ADDRESS (dbghelp's code for "no
  line information").
* SymFunctionTableAccess64 (the RUNTIME_FUNCTION; for another process a copy of its exception directory),
  StackWalk64 (x64 unwinding of the calling process through the caller's routines, leaf frames handled; another process:
  ERROR_NOT_SUPPORTED since its unwind data is not mapped here).
* SymSrvGetFileIndexInfo/W (timestamp, SizeOfImage, RSDS guid/age/pdb of a PE file on disk).
* UnDecorateSymbolName/W: undecorated names copied as dbghelp does; MSVC "?" names need the full C++ type grammar, which is
  not implemented: 0, ERROR_NOT_SUPPORTED (explicit).
* MiniDumpWriteDump: a real minidump of the calling process - SystemInfo (RtlGetVersion, CPUID), ThreadList (the calling
  thread or the ExceptionParam thread when it is this one, with CONTEXT and stack), ModuleList (VS_FIXEDFILEINFO from the
  in-memory resource and the CodeView record), MemoryList (the stack), Exception, MiscInfo, user streams. The kernel
  exposes no thread enumeration (no Thread32First), so other threads are not in the dump; another process: ERROR_NOT_SUPPORTED;
  callbacks: ERROR_NOT_SUPPORTED. Header Flags record MiniDumpNormal whatever type bits were asked.
* ImagehlpApiVersion/Ex.

`t_u_dbghelp.c` (52 checks): SymFromAddr must name `CreateFileW` at the address GetProcAddress gives, SymGetModuleInfo64
must match the PE header in memory, StackWalk64 must cross the program's own known call chain (depth_walk <- frame_c <-
frame_b <- frame_a <- main), SymSrvGetFileIndexInfoW on the program's own file must match its loaded header, and the
minidump is re-read and its streams parsed (signature, version, directory bounds, thread context = the captured one,
exception record, modules with 10.0.x version info, process id).

## 5. Step 4 — advapi32.dll additions (`dlls/advapi32/svc.c`, `module.json`, test `t_u_advapi32.c`)

The largest fn-missing set among chrome.dll's delay-loads (24 names). The 9 CryptoAPI names (and the other 30 cryptsp
exports advapi32 carries on Windows) are export forwarders to cryptsp.dll (the Wine port) - exactly Windows' arrangement -
so `advapi32!CryptGenRandom` is `cryptsp!CryptGenRandom`, loaded on first use. The servers the remaining names talk to do

ERROR_INVALID_HANDLE; RegisterEventSourceW/A RPC_S_SERVER_UNAVAILABLE, ReportEventW/A and DeregisterEventSource

LsaEnumerateAccountRights/LsaFreeMemory STATUS_INVALID_HANDLE; LogonUserW/A, CreateProcessWithLogonW,
ImpersonateAnonymousToken ERROR_NOT_SUPPORTED; CreateProcessWithTokenW = CreateProcessAsUserW's rules (the default token
works, any other is refused). Real: AllocateLocallyUniqueId ({counter, pid}; unique among live processes - a system-wide
allocator would need a kernel service, noted for K4), GetFileSecurityW/A (= GetNamedSecurityInfoW's descriptor),
SetFileSecurityW/A (ERROR_NOT_SUPPORTED, as SetNamedSecurityInfoW: the file systems store no descriptors).

## 13. Run 7 (GUEST_RUN, `--enable-logging=stderr --v=1`): a crash the quieter run does not reach

Same tree as run 6, only `--v=1` added to the command line to see what precedes the `base::expected` CHECK. It ends
differently, after 26.7 s: `process chrome.exe (pid 60) killed: vector 14 error 6 ... cr2 7ffffda2fff0 status c0000005`
= a **stack overflow** (write just below the thread's stack) in thread 208, caused by an exception-dispatch loop:

1. `dnsapi.dll not loaded` (probe, fine) and `ERROR:net\dns\dns_config_service_win.cc:526 DNS registry watch failed to
   start` are the last Chromium lines; then thread 208 takes `first-chance c0000005 at 0 (8 0)`, an *execute* fault at
   RIP 0 (a call through a NULL function pointer);
2. the vectored handler of the Wine ports (`wineport/glue/seh.c: shzw_teb_frames_veh`, statically linked into every Wine
   module; the frame in `cryptsp.dll` is the copy that was first in the handler list) then faults itself: `first-chance
   c0000005 at cryptsp.dll+fbfa (0 0)` = its load `tib->ExceptionList` (`mov (%r12),%rbx` with `r12 = gs:[0x30]`) read
   address 0, i.e. **`gs:[0x30]` (the TEB self pointer) is 0 on that thread while the handler runs**;
3. each nested fault re-enters the handler (256 nested first-chance records for tid 208, 0x780 bytes of stack each) until the
   stack is exhausted.

Two separate defects, neither fixable inside K5's directories alone:
* **Kernel/ntdll (K4):** why is `gs:[0x30]` 0 for a thread that is running user code and dispatching an exception? Candidate:
  a thread whose TEB was already torn down or never set up (thread 208 is a worker created after `DnsConfigServiceWin`
  started; the RIP-0 call may itself be a call through a freed/unloaded module's import). `first-chance ... at 0 (8 0)` is
  the first event to explain.
* **Wineport glue (K5's `wineport/glue/seh.c`, files under `shizukudos/win64/`):** the handler must not fault recursively.
  Fix planned but not done in this session: guard the handler with a per-thread re-entrancy flag kept in the TEB's
  user-defined slot (or check `NtCurrentTeb() != NULL` before dereferencing, and return EXCEPTION_CONTINUE_SEARCH when the
  handler is re-entered), so a corrupt TEB turns into the ordinary unhandled-exception path (a clear
  `K64 EXCEPTION` kill) instead of a stack overflow that hides the original fault.

This also means the quieter run's `base::expected` CHECK and this crash are probably different consequences of the same
early condition (the DNS configuration path after `dnsapi.dll` is missing); the honest next step for K5 is a minimal
`dnsapi.dll` (DnsQueryConfig/DnsFree/DnsFlushResolverCache... as explicit failures) so that path takes Chromium's
"cannot read DNS configuration" branch instead of whatever pointer it calls when the module is absent.
