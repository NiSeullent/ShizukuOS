## 1. `shzpnp load` / `unload` / `status` end to end (done, `GUEST_RUN`)

Kernel (`shizukudos/kernel64/ntdrv_*.c`, `ntsys.h`):

- `NtUnloadDriver` (syscall 0xe2): finds the started image of the service, refuses with `STATUS_CONNECTION_IN_USE` when
  another loaded image imports from it and with `STATUS_INVALID_DEVICE_REQUEST` when the driver has no `DriverUnload`
  (it stays loaded, as on Windows), else runs `DriverUnload`, releases the PCI claims and marks the record not started.
- `NtShzDriverQuery` (0xe3, private): one `shz_driver_info_t` per started image — service, image window, device-object
  count and names, the PCI functions claimed for it, export-driver/users flags.
- On a successful `NtLoadDriver` the host walks `HKLM\SYSTEM\CurrentControlSet\Enum\PCI\<hwid>\B<bus>D<dev>F<fn>` and
  claims every function whose `Service` names the service (`pci_claim` → `ntdrv:<service>`, visible through
  `NtQuerySystemInformation` 0x101 and the status screen); unload releases them.
- The loader resolves imports from modules other than `ntoskrnl.exe`/`hal.dll` by loading
  `\SHZ\SYS64\DRIVERS\<dll>` on demand (its `DriverEntry` runs, as a boot-start dependency's would on Windows) and
  looking the symbol up in that image's export directory (bounds-checked; forwarders refused). A missing module is
  reported once; every unresolved symbol is still reported by name and the load is refused.
- Every `DRIVER_OBJECT` now carries `DriverName` (`\Driver\<service>`), a `DRIVER_EXTENSION` (`ServiceKeyName`,
  `AddDevice`) and `HardwareDatabase`, as on Windows (`NdisMRegisterMiniport` writes `DriverExtension->AddDevice`).

`shzpnp` (`shizukudos/win64/apps/shzpnp/shzpnp.c`):

- `load <service>` prints the service key (`Type`, `Start`, `ImagePath` and the file it resolves to under the service
  control manager's rules), refuses non-kernel or disabled services and a missing image file with a message (exit 2),
  calls `NtLoadDriver` and reports the status in words (`STATUS_IMAGE_ALREADY_LOADED`, `STATUS_INVALID_IMAGE_FORMAT`,
  `STATUS_PROCEDURE_NOT_FOUND` = unresolved imports named in the kernel log, `STATUS_OBJECT_NAME_NOT_FOUND`), then
  prints the driver's status record (device objects, PCI functions).
- `unload <service>`, `status [<service>]` (exit 1 when the service is not loaded, 3 without the driver host).

Test `T_DRV_LOAD.EXE` (`shizukudos/win64/tests/t_drv_load.c`; runs in the default WIN64.IMG, so in
`run_k64_standalone.py` and `run_k64_gui.py`): packages the unmodified `ECHO.SYS` test driver (now shipped as test
data `\SHZ\TESTS\ECHO.SYS`) with a synthetic decorated INF for the last unclaimed non-display PCI function of the
Kernel64 bus scan; `add-driver --install` → `load` → the function reads `ntdrv:shzecho` in the claim registry →
`\\.\ShzEcho` opens and an IOCTL round-trips through the loaded driver → `status` → second `load` = already loaded →
error paths (no service key; missing image; non-PE image; a copy of ECHO.SYS whose import `IoCreateDevice` was renamed
in the file → refused with `STATUS_PROCEDURE_NOT_FOUND`), all without a kernel fault → `unload` (claim released,
device gone) → `load` again (left loaded so the status screen shows the claim). **31/31 PASS**.

`T_SHZPNP.EXE` no longer assumes its INF is published as `oem0.inf` (T_DRV_LOAD publishes one first): it finds its
`oem<N>.inf` through the `DriverDatabase\DriverInfFiles` record. 35/35 PASS.

`IRP_MN_START_DEVICE` = 0 means NDIS's `NdisIPnPStartDevice` ran the miniport's `MiniportInitialize` to completion on the
NIC (bus-interface config reads, the three resources, BAR0 mapped, DMA rings from `AllocateCommonBuffer`, chip reset,
EEPROM MAC read, `IoConnectInterrupt` on line 10, TX/RX enabled) and then queried its OIDs and enabled the device
interface. The guest program also confirms `ntdrv:e1000` in the claim registry, `\Device\{NetCfgInstanceId}` among the
host's device objects, and opens that device from user mode (`IRP_MJ_CREATE` through NDIS). Not done: no NDIS protocol
(no TCP/IP) is bound above the miniport, so no packet is sent or received through it; that is the next layer, not this
brief.

What it took (all in `shizukudos/kernel64/ntdrv_*.c`, no change to `dlls/`, `kernel32/`, `ntdll/`):

- 40 exports (measured with `pefile` against the two images before writing any): `RtlQueryRegistryValues` (full table
  semantics: SUBKEY/TOPKEY/REQUIRED/NOVALUE/NOEXPAND/DIRECT, MULTI_SZ delivered per string, defaults),
  `IoGetDeviceProperty`, `IoOpenDeviceRegistryKey`, `IoRegisterDeviceInterface`/`IoSetDeviceInterfaceState`,
  `IoGetDmaAdapter` (+ `DMA_OPERATIONS`: common buffers, scatter/gather from MDLs, map transfer), `IoAllocate/
  GetDriverObjectExtension`, `IoRegister/UnregisterShutdownNotification`, `PoCallDriver`, `PoStartNextPowerIrp`,
  `IoBuildPartialMdl`, `ExQueueWorkItem`, `ExInterlockedInsert{Head,Tail}List`/`RemoveHeadList`/`AddUlong`/
  `AddLargeInteger`, `ExpInterlockedPush/PopEntrySList` (the real x64 `SLIST_HEADER` encoding), `ExGetCurrentProcessor
  Counts/CpuUsage`, `KeGetRecommendedSharedDataAlignment`, `KeRegister/DeregisterBugCheckCallback`, `KeNumberProcessors`
  (a data export), `RtlCompareString`, `RtlInitString`, `RtlUnicodeStringToInteger`, `RtlUpcaseUnicodeString`,
  `ZwEnumerateKey`, `ZwQueryInformationFile`, `wcscat/wcscpy/wcslen/wcsncat/wcsncmp/wcsncpy`, `HalTranslateBusAddress`.
  Provider surface 185 → 225.
- Export drivers (ntdrv_ldr.c): an import from a module other than ntoskrnl/hal loads `\SHZ\SYS64\DRIVERS\<dll>` first
  (DriverEntry run) and resolves against its export directory; users are counted (unload refused while in use).
- `ntdrv_pnp.c`: the PnP root (PDO per bound devnode, AddDevice, IRP_MN_START_DEVICE with CM_RESOURCE_LISTs from the
  BARs and interrupt line, `IRP_MN_QUERY_INTERFACE` → `BUS_INTERFACE_STANDARD`), device properties, device/driver registry
  keys, device interfaces, driver-object extensions, the DMA adapter. Struct layouts measured from Microsoft's wdm.h with
  mingw and asserted in the source (`CM_PARTIAL_RESOURCE_DESCRIPTOR` 0x14 under pack(4), `BUS_INTERFACE_STANDARD` 0x40,
  `DMA_OPERATIONS` 0x80, `DEVICE_DESCRIPTION` 0x28, `RTL_QUERY_REGISTRY_TABLE` 0x38, `KBUGCHECK_CALLBACK_RECORD` 0x40, ...).
- Every `DRIVER_OBJECT` gets a `DRIVER_EXTENSION` (`NdisMRegisterMiniport` writes `DriverExtension->AddDevice`),
  `DriverName` and `HardwareDatabase`.
- **IRQL is CR8 now.** The first start attempt panicked in `MiniDoRequest` ("KeAcquireSpinLockAtDpcLevel below
  DISPATCH"): the DDK's amd64 headers inline `KeGetCurrentIrql`/`KfRaiseIrql`/`KeLowerIrql` as CR8 reads/writes, so
  unmodified x64 drivers raise IRQL without calling any export (ndis.sys: 85 CR8 instructions) and the host's software
  IRQL never saw it. The host keeps no software copy any more: providers read CR8, raise/lower write it, and
  `sched_tick()` (sched.c, the one shared-file change) does not preempt while CR8 >= 2. The default runners are
  unaffected (verified below).
- shzpnp: the Net class installer's registry output for `Class=Net` (NetCfgInstanceId, Characteristics, BusType,
  ComponentId, Linkage\Export/RootDevice, the service's Linkage, the Connection record) — what NDIS's AddDevice reads.

Two host bugs found by this driver and fixed on the way: `IoGetDeviceProperty` with a zero-length query must return
`STATUS_BUFFER_TOO_SMALL` with the length (NDIS sizes its buffer that way); the resource-list log walked a `[1]` array
and GCC -O2 cut the loop to one iteration (only the log; the list the driver received was complete) — now a flexible
array member.

## Not done / caveats (truthfully)

- No packets: nothing binds to the NDIS miniport (no protocol driver, no TCP/IP on this side).
- The e1000 INF is undecorated, so it installs only with `--legacy`; a Windows 10 vendor INF would not need it.
- `IoRegisterDeviceInterface` records the link name but does not publish it in the object namespace.
- `MmUnmapIoSpace`, image pages and DRIVER_OBJECTs are retained across unload (bring-up arena, as before).
- The DMA adapter has no real map registers; `AllocateAdapterChannel` calls back immediately; `MapTransfer` returns the
  physical address of the contiguous run (correct for the direct-mapped kernel heap).
- The "no kernel fault" check of `run_k64_pnp.py` looks for the kernel's PANIC line; a triple fault would show as a
  timeout.
