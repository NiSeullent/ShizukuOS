## 1. `shzpnp load` / `unload` / `status` end to end (done, `GUEST_RUN`)

Kernel (`shizukudos/kernel64/ntdrv_*.c`, `ntsys.h`):

- `NtUnloadDriver` (syscall 0xe2): finds the started image of the service, refuses with `STATUS_CONNECTION_IN_USE` when
  another loaded image imports from it and with `STATUS_INVALID_DEVICE_REQUEST` when the driver has no `DriverUnload`
  (it stays loaded, as on Windows), else runs `DriverUnload`, releases the PCI claims and marks the record not started.
- `NtShzDriverQuery` (0xe3, private): one `shz_driver_info_t` per started image — service, image window, device-object
  count and names, the PCI functions claimed for it, export-driver/users flags.
- On a successful `NtLoadDriver` the host walks `HKLM\SYSTEM\CurrentControlSet\Enum\PCI\<hwid>\B<bus>D<dev>F<fn>` and
  claims every function whose `Service` names the service (`pci_claim` → `ntdrv:<service>`, visible through
  `NtQuerySystemInformation` 0x101 and the status screen); unload releases them.
- The loader resolves imports from modules other than `ntoskrnl.exe`/`hal.dll` by loading
  `\SHZ\SYS64\DRIVERS\<dll>` on demand (its `DriverEntry` runs, as a boot-start dependency's would on Windows) and
  looking the symbol up in that image's export directory (bounds-checked; forwarders refused). A missing module is
  reported once; every unresolved symbol is still reported by name and the load is refused.
- Every `DRIVER_OBJECT` now carries `DriverName` (`\Driver\<service>`), a `DRIVER_EXTENSION` (`ServiceKeyName`,
  `AddDevice`) and `HardwareDatabase`, as on Windows (`NdisMRegisterMiniport` writes `DriverExtension->AddDevice`).

`shzpnp` (`shizukudos/win64/apps/shzpnp/shzpnp.c`):

- `load <service>` prints the service key (`Type`, `Start`, `ImagePath` and the file it resolves to under the service
  control manager's rules), refuses non-kernel or disabled services and a missing image file with a message (exit 2),
  calls `NtLoadDriver` and reports the status in words (`STATUS_IMAGE_ALREADY_LOADED`, `STATUS_INVALID_IMAGE_FORMAT`,
  `STATUS_PROCEDURE_NOT_FOUND` = unresolved imports named in the kernel log, `STATUS_OBJECT_NAME_NOT_FOUND`), then
  prints the driver's status record (device objects, PCI functions).
- `unload <service>`, `status [<service>]` (exit 1 when the service is not loaded, 3 without the driver host).

Test `T_DRV_LOAD.EXE` (`shizukudos/win64/tests/t_drv_load.c`; runs in the default WIN64.IMG, so in
`run_k64_standalone.py` and `run_k64_gui.py`): packages the unmodified `ECHO.SYS` test driver (now shipped as test
data `\SHZ\TESTS\ECHO.SYS`) with a synthetic decorated INF for the last unclaimed non-display PCI function of the
Kernel64 bus scan; `add-driver --install` → `load` → the function reads `ntdrv:shzecho` in the claim registry →
`\\.\ShzEcho` opens and an IOCTL round-trips through the loaded driver → `status` → second `load` = already loaded →
error paths (no service key; missing image; non-PE image; a copy of ECHO.SYS whose import `IoCreateDevice` was renamed
in the file → refused with `STATUS_PROCEDURE_NOT_FOUND`), all without a kernel fault → `unload` (claim released,
device gone) → `load` again (left loaded so the status screen shows the claim). **31/31 PASS**.

`T_SHZPNP.EXE` no longer assumes its INF is published as `oem0.inf` (T_DRV_LOAD publishes one first): it finds its
`oem<N>.inf` through the `DriverDatabase\DriverInfFiles` record. 35/35 PASS.
