# ShizukuDOS 10: NT driver corpus

The NT driver host (Kernel64, `ntdrv_*.c`) has to be measured against kernel-mode drivers nobody here wrote. This
corpus is real Windows-architecture driver source — ReactOS's x64 WDM, NDIS, StorPort/SCSI-port and KMDF drivers,
the KMDF runtime itself, and the virtio-win drivers — built, unmodified, by a script, plus the tools that say what each
`.sys` needs from the kernel. No Microsoft or Intel binary is used, downloaded or committed; vendor packages are
measured on the user's own copy with the same tools.

Reproduce:

```
python3 shizukudos/ntdrv/corpus/fetch.py              # ReactOS, virtio-win, Microsoft WDF at the manifest pins
python3 shizukudos/ntdrv/corpus/build.py --packages   # build/shizukudos/ntdrv/corpus/build-result.json
python3 shizukudos/win64/tools/import_coverage.py build/shizukudos/ntdrv/corpus --providers [--exports <json>]
```

Host requirements beyond the repository's usual ones: `libgmp-dev` (the GCC plugin headers include `gmp.h`),
`flex` and `bison` (ReactOS's widl), `g++`.

## How the ReactOS drivers are built

`build.py` builds every driver from its own `CMakeLists.txt`. A small evaluator (`CMakeLite`) runs the subset of CMake
those files use — `set/list/if/foreach/include`, `add_definitions`, `include_directories`, `add_library`,
`target_compile_definitions/options/include_directories`, `target_link_libraries`, and the ReactOS macros
`add_importlibs`, `set_module_type`, `spec2def`, `add_asm_files`, `add_driver_inf` — so sources, defines, include
paths and libraries are the driver's own. Static libraries a driver links (arbiter, dmilib, virtio, sptilib,
ntoskrnl_vista, libcntpr, wdfdriverentry, aux_klib, usbdex, wdmguid) are found by indexing every `add_library()`
of the tree and built the same way. The state every ReactOS target inherits (definitions, include directories,
`CMAKE_INCLUDE_CURRENT_DIR`) and the compile options are copied from the top-level `CMakeLists.txt` and
`sdk/cmake/gcc.cmake` for ARCH=amd64, Release. Linking follows `set_module_type(... kernelmodedriver)`:
`--subsystem native:5.01`, entry `DriverEntry` (`FxDriverEntry` for `kmdfdriver`), image base 0x10000,
`init-section.lds`, then `pefixup --kernelmodedriver`.

Everything ReactOS's build generates is generated by ReactOS's own host tools, compiled from the pinned tree:
`hpp` (wdm.h, ntddk.h, ntifs.h, ntdef.h, winnt.h, devioctl.h from the xdk templates), `windmc` after the UTF-16
conversion `utf16le` does (bugcodes.h, ntstatus.h, ...), `spec2def` (import libraries of ntoskrnl, hal, ndis,
storport, scsiport, classpnp, wdfldr, wmilib, hidclass, hidparse, ks, portcls, usbd, videoprt, and the `.def`/stubs
of modules that export an API), `widl` + `wpp` (flex/bison; 183 psdk IDL headers), `asmpp` (MASM `.asm` -> GAS),
`geninc` (`ksamd64.inc` from `genincdata`), `pefixup`, and `gcc_plugin_seh`.

Structured exception handling: ReactOS's amd64 GCC build uses its own GCC plugin for `_SEH2_TRY`; the plugin is built
against the cross compiler's plugin headers and loaded exactly as ReactOS does, so the GCC-built drivers have real
SEH (`"seh"` in build-result.json). C++ (uniata, wdf01000, cdrom, hdaudbus) is compiled with
`x86_64-w64-mingw32-g++` when installed, else `clang++ --target=x86_64-w64-mingw32`; the record says which
(`cxx_compiler`). All linking is GNU ld. The compiler support library `libgcc.a` is on the link line so that
`___chkstk_ms` would resolve if a driver needed it; `libgcc_chkstk` records whether it was used (never, so far).

Toolchain of the recorded run: x86_64-w64-mingw32-gcc/g++ 13-win32 (all C and C++ of the ReactOS table), clang 18.1.3
(only used for the virtio-win retries).

What this means for the driver host: only ntoskrnl.exe and hal.dll have to be implemented in the kernel. ndis,

unmodified, and then needs the union of their ntoskrnl/hal imports (313 + 12).

The export list of the driver host is not merged yet, so the committed numbers are raw lists. A dated snapshot, for
orientation only: fed with the 170 ntoskrnl and 10 hal exports of the NT-driver-host work in progress
(`ntdrv_prov.c`, 2026-09-29), 101 of the 313 ntoskrnl imports and 4 of the 12 hal imports resolve; `null.sys` misses one
function (`MmPageEntireDriver`), everything else misses more. Re-run with `--exports` when the export JSON lands.

## virtio-win

The current virtio-win drivers are MSBuild/WDK projects. `build.py` evaluates each `.vcxproj` for
"Win10 Release|x64" (`corpus/vcxproj.py`: PropertyGroup/ItemDefinitionGroup/ClCompile with their Conditions, the
project's own `.props`, the WDK defaults NTDDI_VERSION 0x0A000000, KMDF version macros) and compiles it with the corpus
toolchain against the ReactOS headers standing in for the WDK. The sources are written for a case-insensitive file
system (`#include "virtio.h"` for `VirtIO.h`, `..\Virtio`): the build resolves such includes the way Windows would,
with symlinks in a per-driver directory, and records each one.

| driver | project | GCC (mingw) result | first blocker after that (clang, MSVC mode) | verdict |
|---|---|---|---|---|
| viostor | StorPort miniport, WDM, `storport.lib virtiolib.lib wdm.lib` | fails: MSVC dialect (`static __forceinline`) | ReactOS `storport.h` lacks the Windows 8+ extended SRB (`STORAGE_REQUEST_BLOCK`, `SRBEX_DATA`, `STOR_ADDR_BTL8`) | needs WDK headers (+ `wdm.lib`) |
| NetKVM | NDIS 6.85/6.86 miniport, C++ | fails: ReactOS `ndis.h` knows NDIS up to 6.20 | NDIS 6.8x declarations missing (`NDIS_POLL_*`, `NDIS_CURRENT_IRQL`, ...) | needs WDK headers and an NDIS 6.8x provider |
| vioinput | HID minidriver, KMDF 1.15 | fails: MSVC dialect | WPP trace headers (`Array.tmh`) are generated by the WDK's `tracewpp` | needs WDK tools |
| viogpudo | WDDM display-only driver, C++ (`displib.lib`) | fails: GUID redefinitions between ReactOS `d3dnthal.h` and the DDI headers | the same, plus `dllimport` definitions | needs WDK headers, `displib.lib`, and dxgkrnl at run time |

None of the four builds without the WDK. The older NetKVM (NDIS 5.1) that ReactOS carries builds and is in the
ReactOS table.

## Microsoft Windows-Driver-Frameworks (MIT)

The repository publishes the KMDF and UMDF v2 sources and the public headers for KMDF 1.15 to 1.33, but no build
description (no `.vcxproj`, `sources` or `dirs` files): its stated purpose is reading and step-through debugging. It
cannot be built as-is here. ReactOS carries an older copy of the same sources (KMDF 1.17, from upstream commit
d9c6040, with a CMake build and small `reactos_special.*` shims), and that copy is built unmodified above:
`wdf01000.sys` (1.36 MB) and `wdfldr.sys`, plus two real KMDF clients (cdrom, hdaudbus).

Version limit: `FxLibraryCommonRegisterClient` (sdk/lib/drivers/wdf/kmdf/src/librarycommon/fxlibrarycommon.cpp) refuses
a client whose WDF function table is larger than the runtime's ("version mismatch detected in function table count").
A 1.17 runtime therefore binds drivers built for KMDF <= 1.17. Windows 10/11 driver packages declare
`KmdfLibraryVersion` in their INF (`[*.Wdf]` -> `KmdfService` section; `test_inf.py --package` prints it); those
built for 1.19-1.33 need the newer framework, i.e. the Microsoft sources at the pinned commit given a build
description, or a ReactOS update.

## What Windows 10 Intel driver families need

Which framework each family is written against, and therefore which provider the driver host must supply. This comes
from the frameworks' public documentation and the directives such INFs carry, not from Intel binaries (none are
here); for a real package run `test_inf.py --package` (INF view: Class, services, KMDF version) and
`import_coverage.py --providers` (import view) on the user's copy.

| family | framework | needs from the host |
|---|---|---|
| Ethernet (e1d/e1i/e2f... 1GbE, I219/I225/I226) | NDIS 6.x miniport (6.30-6.8x) | ndis.sys with NDIS 6.x (NET_BUFFER, NdisMRegisterMiniportDriver); ReactOS's ndis.sys is NDIS 5.x |
| Wi-Fi (Netwtw*) | NDIS 6.x + WDI (WLAN Device Driver Interface) | NDIS 6.5+, Microsoft's WDI UE (wdiwifi.sys), the WLAN service stack |
| Rapid Storage / VMD (iaStorAC, iaStorVD) | StorPort miniport | storport.sys with the Windows 8+ extended SRB API (ReactOS's lacks it, see viostor) |
| Chipset / platform INFs | INF-only (no .sys); `Include`/`Needs` of Windows inbox INFs such as machine.inf, pci.inf | an inbox INF set: ShizukuDOS has none, so these add names to devices at most |
| Serial IO (I2C, SPI, UART, GPIO), ME/HECI, Thunderbolt, DPTF, Bluetooth | KMDF (usually 1.15+), plus SpbCx/GpioClx/UCX class extensions for Serial IO/USB | Wdf01000 at the declared KMDF version and the class extensions |
| Smart Sound Technology / HD audio | KMDF bus drivers + PortCls/AVStream miniports | Wdf01000, portcls.sys, ks.sys, the audio engine |
| Graphics (igdkmd64 / igdkmdn64 / igdkmdnd64) | WDDM 2.x kernel-mode driver + user-mode D3D drivers | dxgkrnl.sys (not available) |

**WDDM 2.x not available — what that means.** A WDDM kernel-mode display driver imports almost nothing directly
(`DxgkInitialize` from dxgkrnl.sys); it hands the DirectX graphics kernel a table of over a hundred DDI callbacks and
from then on dxgkrnl drives it: display topology (VidPN), the GPU scheduler and preemption, the video memory manager
with GPU virtual addressing (WDDM 2.0+), paging, fences, power, and the kernel side of every D3D call. The user-mode
half (Intel's D3D9/11/12, OpenCL, media DLLs) is loaded by the D3D runtime (d3d11/d3d12, dxgi, the D3DKMT thunks in
gdi32) and talks to its kernel half only through dxgkrnl. ShizukuDOS has none of that: no dxgkrnl, no D3D runtime, no
display-miniport host. The Intel graphics driver cannot load, and nothing short of implementing the WDDM 2.x
kernel and runtime contracts changes that; the framebuffer path Kernel64 has today is unrelated to it.

## Distance to "Win10 Intel drivers install as-is"

* **Install (INF level): close for well-formed packages.** An amd64-decorated Windows 10 INF parses, selects,
  ranks, stages and installs its files and registry with shzpnp today (on the guest: T_SHZPNP.EXE). Gaps: no
  signature/catalog verification, no co-/class installers, no inbox INFs for `Include`/`Needs`, and no PnP
  enumeration feeding devices to it (devices come from `--device` or a boot log until the driver host's PnP
  manager populates Enum).
* **Load: far.** Every Intel family needs a framework provider the host does not have yet: NDIS 6.x (no source here
  provides it; ReactOS's is 5.x), StorPort with extended SRBs (ReactOS's lacks them), KMDF above 1.17 (ReactOS's
  runtime is 1.17; the Microsoft source has no build), SpbCx/GpioClx/UCX/PortCls, and for graphics WDDM 2.x. Even the
  ReactOS corpus, built for exactly the ntoskrnl/hal ABI, needs 313 ntoskrnl and 12 hal functions; the host's work in
  progress resolves 101 of them.
* **Run: not measured.** Nothing here has executed a driver; loading the corpus drivers under the host is the next
  measurement, starting with null.sys (one missing import) and the NDIS 5 / StorPort / KMDF 1.17 clients whose
  providers are in the corpus.
